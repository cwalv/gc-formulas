Foundations: a project journey

From "build a formula pack for cross-repo work" to "maybe the workflow-engine shape is wrong" — and the empirical machinery for the answer.

gc-formulas · project arc through 2026-05-24

The arc, in four phases

This project didn't unfold in the clean "position → evidence → product" order a finished system would imply. The actual story is more interesting and a little more confused. Four phases:

1. The original goal. Build a formula pack for gascity that does cross-repo work in a workweave and serializes merging back to the primary weave. Modeled on projects/foundations/formulas/mol-polecat-base.formula.toml + refinery, generalized for multi-repo.
2. It got harder than expected. Built the foundations-test rig (an isolated gascity rig with its own pools) and outlined three tiers of debuggability investments in docs/archive/debuggability-plan.md, because LLM-in-the-loop iteration was too slow and too lossy. The substrate (beads) and the whole approach kept biting even in the controlled rig. The validation-pack/ as a coherent test surface came later — see phase 4.
3. Stepped back to evaluate the graph.v2 / workflow-engine approach holistically. The conversation in docs/archive/orchestration-conversation.md + docs/archive/gascity-focus-areas.md produced the principles — "prefer content over runtime," "form matches consumer," "opinionated UI for humans / content for agents." The position in docs/position.md is the synthesis from this phase, not the starting point.
4. Figuring out how to test the principles. Validation-pack tests claim 1 (patterns work without a runtime). Plan-evals asks whether the pipeline earns its keep. Throughput-mode (sketched + preliminary data) would close out claims 2/4/5. This is most of the recent commit volume.

The formulas the project set out to build (phase 1) exist today, post-pivot, under the principles that came out of phase 3. Whether the principles deliver on the original goal is what phase 4 is measuring. Read in that order, the rest of the project's shape makes more sense.

Phase 1 — the original goal

Build a formula pack that does cross-repo work in a workweave and serializes the merge back to primary. The pattern was already proven for the single-repo case: projects/foundations/formulas/mol-polecat-base.formula.toml (load context → workspace setup → preflight → implement → self-review) plus a refinery loop that watches for completed work, merges branches, locks, pushes. The job was to generalize.

Concretely, that meant the formula families that now live in formulas/:

Formula familyDrives
mol-weave-base Per-bead workweave lifecycle: workspace discovery / creation / rejection-aware resume. The thin base every variant extends.
mol-weave-work / -do-work / -work-sp Code-authoring variants. Extend base with preflight-tests / implement / self-review steps. "-sp" is the single-pass variant.
mol-weave-refinery The cross-repo merge loop. Rebases and merges every touched ephemeral branch, then locks and pushes a coherent cross-repo snapshot.
gastownhall-upstream + -followup Submitting changes to upstream gastownhall repos. Validates, pushes to fork, opens PR with a {{kind}}(scope): title, defers as a park pattern. Followup handles fixup commits when CI fails.
mol-docs-refresh Refresh the beads-ui handbook against current tips of beads + gastown + gascity (per rwv.lock). Mechanical citation-drift fixes + semantic rewrites + flagged gaps + dated changelog.

These .toml files exist on disk. Whether they currently run end-to-end against real cross-repo workloads isn't measured by anything in this project today; phase 2 surfaced how hard that loop was, and the production-shape exercise of these formulas hasn't been folded back in. They're not the project's center of gravity now — phases 3 and 4 are.

Phase 2 — it got harder than expected

The first attempts to run cross-repo formulas end-to-end stalled in a specific pattern. A 30-minute LLM-driven loop would fail, and the failure mode would be ambiguous — was it the substrate, the persona prompt, the fixture predicate, or the model? From docs/archive/debuggability-plan.md:

The full-scenario LLM iteration loop is too slow and too lossy as a debugging surface. Two of today's bugs (bd#4082, .children vs .dependents) hid behind 30+ minutes of LLM runs that could not disambiguate "substrate lost the write" from "agent didn't perform the step" from "fixture predicate mismatch." A manual 4-second walkthrough surfaced both.

The foundations-test rig and debuggability investments

Phase 2's response was to build a repeatable debugging surface. The foundations-test rig (a separate gascity rig with its own pool definitions) provided isolation from the main foundations city — so substrate experiments wouldn't disturb production work. docs/archive/debuggability-plan.md sketches the three-tier plan that came out of this phase:

  • Tier 1: checkpoint pauses (DEBUG_PAUSE_AT), one-shot inspect script, container preservation. Cheap; immediate leverage.
  • Tier 2: manual driver mode (step-named bash functions, --step CLI), failure-mode classifier in the verifier, predicate-of-predicates ("notes do not contain 'bash' — actual: 'computed sha256 a3f4...'").
  • Tier 3: substrate replay (record every bd op, replay against fresh bd to localize the variable), no-LLM fake-worker mode (deterministic stand-ins that script the bd ops a passing agent would do).

Several of these landed during phase 2 in some form. Most ended up baked into the validation-pack/ later, when that surface got built in phase 4 (the fake-worker lane in particular paid off there — see below). The debuggability-plan itself sits in docs/archive/ now, having served its purpose as a direction-of-travel for the test surface that came after.

What phase 2 surfaced beyond debugging tools
Even with better debugging affordances, getting the formulas to work end-to-end kept turning up substrate-layer issues rather than workflow bugs. The pattern was specific: a workflow-engine architecture papers over substrate bugs as long as the workflow is short and the load is light. Push it harder (multi-repo, longer chains, parallel workers) and the substrate becomes the bottleneck. That's what made phase 3's step-back land — the question stopped being "how do we make this workflow engine work" and became "is the workflow-engine shape the right frame at all."

Phase 3 — the step back

After enough phase-2 sessions where debugging a formula run kept turning up substrate-layer issues, the question shifted from "how do we make this workflow engine work?" to "is the workflow-engine shape the right frame at all?" Two long conversations captured the reasoning:

  • archive/orchestration-conversation.md — landscape mapping (gascity, NTM, Flywheel, Intent, Swamp, LangGraph, Temporal, A2A). Where each one sits, what each one earns its keep doing, what each one over-builds.
  • archive/gascity-focus-areas.md — what to invest in if gascity is going to mature into load-bearing infrastructure rather than an interesting bet. The four focus areas: worker contract crystallization, schema enforcement, reverse derivation, eval coverage for the worker protocol.

The load-bearing realization from those conversations is captured in one line:

Every line of bash in graph-worker.md is a place where the protocol leaks.

And the design principle that follows:

Prefer content over runtime. Anything you can express as a markdown template, skill, or AGENTS.md fragment, prefer that over a DSL + interpreter. The runtime earns its keep only where the artifact genuinely can't be expressed in prose — durable execution semantics, exactly-once side effects, concurrent state mutations.

Out of those came six principles, now in docs/principles.md. Each has a "you're violating this when..." sentence, so violations are nameable rather than abstract:

  • Content over runtime. Markdown templates > DSLs + interpreters. Violating it when you build a TOML format whose contents are read by an LLM, then add a Go interpreter to mediate.
  • Form matches consumer. Agent-facing? Prose. Human-facing? Opinionated UI. Violating it when you parse an LLM's prose output with a regex.
  • Opinionated UI for humans, content for agents. Generalization of the above. Where the artifact is consumed by a human, opinionated UI compresses agreements about how to think. Where it's consumed by a model, prose is the universal interface.
  • Roles live in beads, not personas. The model is the role-system. A single generic worker loop — poll, claim, read bead, do exactly what the bead says, close. Violating it when you have an if persona == "foreman" branch in Go code.
  • Worker contract shrinks as the architecture matures. New features should compress the protocol, not extend it. Violating it when new orchestrator features keep adding sections to the worker prompt.
  • Substrate provides infrastructure, never roles. Sessions, queues, hooks, events — yes. Named roles — no. Violating it when the substrate hard-codes a "mayor" or "treehugger" notion.
Prior art (per Gemini review)
These principles aren't novel; they map onto three established patterns: the Blackboard architecture (1980s AI; shared durable data store, autonomous knowledge sources), Promise Theory (Burgess/CFEngine; autonomous nodes commit to desired states), and the Choreography vs. Orchestration distinction from microservices (event-driven beats top-down for fuzzy work). The contribution isn't the architecture; it's applying it to LLM-driven coding work specifically, with falsifiable claims rather than a stance.

The position in docs/position.md is the synthesis. It reduces the stance to five testable propositions — each is falsifiable, none is "obviously" true. (Status as of 2026-05-24, post phase 4 work to date.)

Phase 4 — testing the principles

Most of the recent commit volume sits here. Two empirical layers:

Where we violate our own principles
Roles are encoded in persona files (foreman, implementer, evaluator, treehugger × 2 shims = 8 files). Phase 3's principle "roles live in beads, not personas" says they shouldn't. We violate it ourselves; captured as an improvement and tracked. The 7 patterns also aren't orthogonal — 02/03/04/05 are variations of one fan-out shape parameterized by (decompose?, N, aggregation). Tolerable as unit-test fixtures; redundant for higher-level validation. Phase 4 surfaced these honestly rather than papering over them.

The substrate fix story

The longest-running puzzle of validation-pack work was a write-loss race that kept eating bd state across concurrent processes. Symptoms: workers claim a bead, exit cleanly, and the bead reverts to open by the next poll. Multiple sessions chased this:

  • First hypothesis: "supervisor-load race" — a startup ordering bug in gc. Patches landed; the problem survived.
  • Second hypothesis: "JSONL auto-export under flock" — wrap exports in a file lock. Built it; the problem survived.
  • Third hypothesis (the right one): bd v1.0.3 has an auto-import-from-JSONL guard that fires on every bd invocation against an empty database. With auto-export on, the JSONL accumulates; concurrent bd processes import the stale state into fresh dolt instances and overwrite the in-dolt writes. Earlier patches tried to disable via ENV BEADS_EXPORT_AUTO=false — that env var doesn't exist in bd v1.0.3 (no-op).

The real fix (commit 805a19e) sets bd config set export.auto false plus deletes .beads/issues.jsonl at image build time. The auto-import guard then trips on info.Size() == 0 and skips entirely. Single source of truth: embedded dolt.

This is also one of the clearer examples of phase 3's principles applying to the substrate's own scope, not just to user-built layers on top. The JSONL auto-import was substrate complexity that wasn't load-bearing for the original design's single-source-of-truth intent; it accreted, and it cost multiple debugging sessions to find. "Content over runtime" applied to beads-itself is partly a cleanup direction — restoring the original substrate intent before workflow-engine surface area drifted in. (Rootless-mode formulas, where the LLM reads the formula content directly through a runtime mediator rather than via materialized beads, are another instance of the same accretion.)

The pipeline-quality layer — plan-evals

Validation-pack proves the substrate can run a pattern. Plan-evals asks: does the multi-agent pipeline (planner → graph → workers → merge) produce correct outcomes more reliably and faster than a single agent could? The full arc is in plan-evals-journey.html — one weekend, 30 commits. Headline findings:

  • The architect / choreographer / worker split is implementable as three separable eval surfaces, not just a framing slide.
  • The choreographer's per-event prompt isolation holds up against batched arrivals (N=10, 0pp gap).
  • Substrate orchestration costs ~3.6× wall vs bare-bash at identical pass-rate. The premium is fixed overhead (city boot, supervisor lifecycle, bd coordination), not per-step inference. The phase-3 principle stance has to defend that premium against tangible alternatives.
  • The choreographer is wall-clock-bound at LOOP_TIMEOUT, not work-bound. The cap, not the work, is the binding constraint.
  • The graph-shape probes (architect layer) surfaced a sharper finding than claim 5's original framing: choreography libraries shift sonnet's defaults but leave opus's untouched. Library curation is architecture work.

Throughput-mode — preliminary data, full build still pending

docs/throughput-mode.md sketches a layer above the unit-test scenarios: N workflow instances draining concurrently, scaling workers up/down, surviving failures without losing the queue. The full design (heterogeneous backlogs, elasticity, fairness) hasn't been built. But the phase-2 validation-pack work produced wall-clock-under-parallel-load data as a side effect — enough to start telling a story.

SubstrateN=1 wallN=7 wallslowdown at N=7
gc94 s242 s2.6×
ntm47 s46 s~1×

Plus the fake-worker lane: all 7 scenarios in parallel under ntm in ~24 s wall-clock. The host has 24 cores + 28% idle + 0.5% IO wait, so the gc slowdown isn't host resource exhaustion.

The finding

gc supervisor parallel startup is dolt-sql-server-bound. The 2.6× slowdown at N=7 is supervisor boot under sql-server contention — an operational ceiling, not a substrate bug. P2 transition storage_degraded → durable takes 21 s solo, 65 s average at N=7. The recommendation in docs/state.md is "serial or ≤3-parallel docker runs" for gc.

ntm scales flat under the same load because it has no reconciler — personas just poll-with-retry to survive ping-pong handoffs. Different trade-off: ntm pays in persona prompt complexity what gc pays in startup contention.

What's still not measured: heterogeneous backlog drain (mixed-pattern queue, total wall to drain), worker elasticity (scale workers up/down with queue), fairness/starvation (does the orchestrator interleave or starve one persona when multiple have work). All three are sketched in throughput-mode.md; building them is the next epic.

The persona contracts as a tracking surface

prompts/pool-worker.md and prompts/refinery.md are the universal contracts. Roles ride on top via bead descriptions. They're also the measurable surface for claim 3 (worker contracts shrink). Today they sit in the low hundreds of lines each — the question is whether they trend down as the substrate matures.

Two load-bearing instructions from each, distilled from real observations:

  • pool-worker.md's "GUPP — If you find work, YOU RUN IT." Forecloses the failure mode where the agent enters a "standing by for confirmation" state instead of executing. Found through repeated observation of workers that found work and asked the human what to do with it.
  • refinery.md's "never offer choices to the operator." If find-work returns nothing, drain and exit; if it returns a bead with bad metadata, reject with the literal problem as rejection_reason and burn the iteration. Don't investigate why.

What we know now, that wasn't load-bearing before phase 3

  1. Claim 1 holds under measurement on both gc and ntm shims, real-LLM and fake-worker modes. 7/7, hermetically.
  2. The substrate fix took three hypotheses. The pattern — "fresh dolt reads stale JSONL, overwrites in-flight writes" — is the kind of thing only re-runnable benches surface. That's the validation-pack earning its keep.
  3. The position's biggest structural learning is the architect / choreographer / worker split. Phase 3's original framing said "model-as-orchestrator"; reality is three roles with three separable failure modes. docs/position.md's terminology note tracks the rename.
  4. Library curation is architect-level work. Choreography idioms aren't a passive menu — they bias weaker model tiers' defaults. Library design is the position-implementing surface.
  5. Substrate orchestration costs ~3.6× wall vs bare-bash at identical pass-rate. Premium is fixed overhead. The phase-3 stance has to defend that premium against a tangible alternative.
  6. Under parallel load (N=7 identical workflows), gc's wall scales 2.6× while ntm's stays flat. The gc bottleneck is dolt-sql-server boot contention, not the substrate itself — operational ceiling, not architectural. ntm's flat scaling comes at the cost of in-persona poll-with-retry.
  7. Two principles we violate ourselves (roles in personas; 7 patterns aren't orthogonal). Honesty about violations is part of the position's stability — naming them is half the discipline.

The meta-story

The honest framing of this project is that it started somewhere and the current center of gravity is somewhere else. Phase 1 set out to build a formula pack. The interesting story is what happened when that didn't go cleanly: phase 2's experience that the workflow-engine architecture started failing under load motivated the phase-3 step back, which produced principles that argue for a different shape entirely — including for the substrate itself, not just for things built on top. Phase 4 is the work of testing whether those principles hold up.

The shape of the work since phase 3 has been consistent across three sub-arcs (validation-pack, plan-evals, formulas-under-new-rules): a short design fragment in docs/ first (<250 lines), implementation second, small smoke to validate, larger run to study what the smoke surfaced. Each implementation has contradicted at least one detail of its fragment. The discipline isn't perfect prediction; it's writing the prediction down so the contradiction has a place to land.

What the project converges on, if the harder claims hold, isn't novel in architecture terms — it's Blackboard plus Promise Theory plus Choreography, applied to LLM coding work. The contribution is treating the position as a falsifiable proposition rather than a stance, with empirical layers built to land the numbers as they become measurable.

What's still in front of us: throughput-mode (the deliberate build, not just incidental data), claim 3's time series, claim 5's counter-experiment, and the persona-contract shrinkage that the principle predicts but hasn't been measured. None of those are conceptually hard; they're the next chapter of phase 4.
